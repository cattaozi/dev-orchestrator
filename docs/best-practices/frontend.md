# Frontend 编码最佳实践

适用范围：`web/frontend/**`

## 1. 架构与分层

- `app/api` 仅做后端代理、协议转换和错误映射，不承载复杂业务逻辑。
- 页面组件负责组合与编排，复杂逻辑下沉到 `lib` 或 hooks。
- 公共能力集中到 `lib`，禁止同类逻辑多处重复实现。

## 2. 配置与网络请求

- 禁止在路由或组件中写死后端地址、端口。
- 后端代理地址统一通过配置层读取（如 `lib/backend-config.ts` + `BACKEND_ORIGIN`）。
- 请求失败返回结构保持一致（至少包含可识别的 `error` 信息与合理 HTTP 状态码）。
- 动态数据页面必须明确缓存策略（如 `force-dynamic` 或 `revalidate`）。

## 3. TypeScript 约束

- 禁止新增 `any`；优先使用 `unknown` 并做类型收窄。
- API 请求和响应应定义清晰类型，避免在调用处临时拼接结构。
- 函数入参与返回值尽量显式声明，降低隐式推断带来的回归风险。

## 4. UI 与交互约束

- 危险操作必须使用自定义 Dialog 二次确认，禁止浏览器原生 `confirm()`。
- Markdown 渲染统一使用 `@/components/ui/markdown`。
- 同时保证桌面端与移动端可用，不提交只在单端可用的布局。

## 5. 组件与状态管理

- 优先复用 shadcn/ui，保持交互与视觉一致性。
- 状态管理遵循“最小共享”原则：局部状态优先，确需跨页面共享再进入 store。
- 控制组件深度和依赖复杂度，避免深层 prop drilling。

## 6. 质量门禁

- 涉及前端行为变更时，至少完成类型检查与构建验证。
- 新增关键用户流程时，补充最小可用的交互测试或验证脚本。
